# Tinker Auto-Train

A scheduled GitHub Actions workflow (`.github/workflows/tinker-auto-train.yaml`) that mirrors the existing SkyPilot `auto-train.yaml`, but drives the Tinker entrypoint (`integrations/fleet/entrypoints/main_fleet_tinker.py`) per (dataset, modality) pair. Per-pair flow:

1. Discover new active Fleet datasets via Supabase
2. Smoke-test (`fleet.make()` on a 2-env sample)
3. Export the task list to `s3://fleet-internal-datasets/{dataset}/openenv/all_{modality}.json`
4. **90/10 deterministic split** into `train_{ds}_{mod}.parquet` + `holdout_{ds}_{mod}.parquet`
5. Run Tinker LoRA training (default base: `moonshotai/Kimi-K2.6`, lora 16, 50 steps)
6. **Held-out eval before train AND after train** → `pre_pass_rate` / `post_pass_rate`
7. Write `eval_results/{ds}_{mod}.json`, upload as workflow artifact, post pre/post/delta to Slack (`#fleet-tinker-runs`)

Both pipelines (SkyPilot + Tinker) consume the same exported S3 JSON but mark `(dataset, modality)` processed in **separate** state files (`.auto_train_state.json` vs `.tinker_auto_train_state.json`).

## Running it

### Cloud (real verification — proves lift on real models)

Requires GitHub secrets: `TINKER_API_KEY`, `FLEET_API_KEY`, `WANDB_API_KEY`, `AWS_*`, `SUPABASE_*`, `SLACK_BOT_TOKEN` (and optional `TINKER_API_URL`).

```bash
gh workflow run tinker-auto-train.yaml \
  -f max_datasets=1 \
  -f modality=tool_use \
  -f num_steps=20 \
  -f base_model=Qwen/Qwen3.5-35B-A3B   # smaller model for a quick proof
```

Then download the artifact:

```bash
gh run download <run-id> -n tinker-eval-results-<run-id>
cat eval_results/*.json | jq '{pre_pass_rate, post_pass_rate, delta, num_steps, n_holdout}'
```

A positive `delta` is the headline number. Per the spec there is **no hard pass/fail gate** — the job exits 0 regardless so you can see flat / negative deltas too.

### Local (orchestration verification — proves wiring, not model lift)

```bash
pytest integrations/fleet/tests/test_tinker_auto_train.py -v
```

Covers all three modalities (`tool_use`, `browser_use`, `computer_use`) with a stub wrapper that emits a fixed pre/post results JSON. Confirms the launcher correctly splits, invokes the script, parses results, and surfaces the delta.

For a fuller dry-run that exercises real discovery + smoke + S3 export (no Tinker call):

```bash
TINKER_API_KEY=dummy FLEET_API_KEY=... SUPABASE_URL=... SUPABASE_KEY=... \
AWS_ACCESS_KEY_ID=... AWS_SECRET_ACCESS_KEY=... \
python -m integrations.fleet.auto_train --backend tinker trigger \
  --dry-run --max-datasets 1 --modality tool_use
```

## CLI

```
python -m integrations.fleet.auto_train --backend tinker trigger \
    [--modality {tool_use,browser_use,computer_use}] \
    [--dry-run] [--skip-smoke] \
    [--team-id ...] [--max-datasets N] [--ignore-seed] \
    [--tinker-base-model HF_ID]   # default: moonshotai/Kimi-K2.6
    [--tinker-num-steps N]        # default: 50
    [--tinker-lora-rank N]        # default: 16

python -m integrations.fleet.auto_train --backend tinker status
python -m integrations.fleet.auto_train --backend tinker seed [--force]
```

## Modality coverage

All three modalities go through the same `FleetTaskEnv` agentic harness in `main_fleet_tinker.py`. VL modalities (`browser_use`, `computer_use`) require a VL-capable base model — the default `moonshotai/Kimi-K2.6` is VL-capable, as are the `Qwen3.5-*` and `Qwen3-VL-*` families.

If you need to swap models per modality, do it via the `base_model` workflow input on a per-run basis (the modality-aware default routing is not yet wired — track in a follow-up).
